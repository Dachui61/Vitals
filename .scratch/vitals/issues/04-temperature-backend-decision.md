# 温度后端选型与降级契约

## Question

**已确定的部分**（来自票 21 同轮的回答，不需要再讨论）：

- 后端 = **`/usr/lib/libSMC.dylib` 无特权读取**（dlopen + `SMCOpenConnectionWithDefaultService` / `SMCReadKeyAsNumeric` / `SMCGetKeyInfo`）。接受使用私有 dylib，**前提是能力探测 + 自动降级**：dlopen 失败、符号缺失、连接失败、键不存在、读值越界——任一情况都退到 thermalState 四档并在界面写明原因。
- 可信度标注：若 CPU die 键的身份只是**推断**出来的，界面照常显示读数，但必须标为**近似值**并显示实际传感器名（如「Tp05·近似」），不得冒充权威值。
- 热压力等级独立成行、四档、**不叫"温度"**；温度类阈值告警在后端不可用时按"不可用"处理，不得静默不触发；等级类告警保留。
- 不引入特权组件（票 21），所以本票的选项里不再有特权路径。

**票 23 已把事实定死**，本票只剩两个产品决策：

1. **探针策略**：主键已定案为 `Tp0j`（降级链 `Tp0j → Tp0g → Tp09 → Tp07 → Tp0b → Tp05 → Tp0m → Tp0L`）。但键语义与芯片/机型相关，只对本机成立——所以 app 是**直接读 `Tp0j`**（本机专用，零启动开销）、**每次启动跑一次探测**（枚举 `T*` 候选 → 1–2 s 单线程 userInteractive 负载 → 取涨幅最大的键；本机唯一选出 `Tp0j`），还是**惰性探测**（先读 `Tp0j`，缺失/越界才探测）？要一并定：探测用的负载要不要在界面上告知用户（它会短暂占用 CPU）、探测结果要不要落盘（换机型/系统升级后可能要重探）。
2. **要不要同时展示 SoC 封装热点**：`TVD0` 一族是整机最热处（单核满载 73 °C，比 CPU die 的 65 °C 更接近这台机器真正的热天花板），CPU+GPU 负载都会推高它。它不是 CPU die，不能叫"温度"，但对"电脑健康"可能比 CPU die 更有意义。要定：只显示核心温度（`Tp0j`，近似值），还是悬浮窗里并列两个（核心温度 + SoC 热点），菜单栏迷你读数是否也带上。

依据 01（IOReportHub 不可行，但发现 libSMC 可无特权读数值温度）与 23（哪个键是 CPU die）的结论，**数值 CPU 温度**最终走哪条后端？

**已被排除**：
- IOReportHub——macOS 27 的通道空间里没有 CPU die 温度通道，且原始样本缓冲区被 KERN_NO_SPACE 挡住（票 01）。
- 特权 powermetrics——macOS 27 已无 smc sampler，root 也拿不到 die 温度（票 02）。
- 特权组件——票 21 决定不装。

**候选**：
- (a) **`/usr/lib/libSMC.dylib`（无特权）**——单次读 ~100 µs，1 Hz 无压力。需票 23 定下"CPU die 是哪个键"。
- (b) **thermalState 四档**——公开 API，零成本，唯一的保底。
- (c) **组合**：(a) 优先，失败降 (b)，再失败显示"不可用 + 原因"。

同时要在本票定下**降级契约**（写进 SPEC，不能含糊）：

- 后端不可用时界面显示什么：温度栏显示"温度不可用（原因）"占位，还是直接隐藏温度栏？
- 降级到 thermalState 四档时，告警如何表现（只保留 CPU 阈值？温度告警自动禁用？）
- "传感器名"的展示规则：主传感器如何选（多个候选键时按什么优先级）、无特权读到时如何标注"近似值"、特权读到时如何标注来源。
- 温度数据的可信度标注：什么情况下必须显示"近似"徽标。

产出：本票的结论 = 一段决策陈述（含选型、优先级、失败降级路径、可信度标注规则），并作为 ADR「温度后端与降级策略」的素材。

## Answer

**温度后端契约定稿**（后端 + 键 + 探针 + 标注 + 降级链，全部有据可依）：

**1. 后端**：`/usr/lib/libSMC.dylib`（无特权）。dlopen + `SMCOpenConnectionWithDefaultService` / `SMCReadKeyAsNumeric` / `SMCGetKeyInfo`；键打包**大端**（`'T'<<24|'C'<<16|'0'<<8|'P'`）。单次读 ~100 µs。

**2. 主键与降级顺序**（票 23 实测）：主用 `Tp0j`；降级链 `Tp0j → Tp0g → Tp09 → Tp07 → Tp0b → Tp05 → Tp0m → Tp0L`。**禁用**：`Tg*`（GPU 侧）、`TVD0/TVDC/TVDP/TCMb`（SoC 封装热点，当作 CPU 会误报）、`TH0x/TH0a/TH0b/TMVR/TR*d/TW0P/TT0P/TVN*/TN00`（环境/板级，CPU 负载下不动）。

**3. 探针策略（惰性探测）**：平时直接读 `Tp0j`，**零额外开销**；只有在读不到（键不存在/rc≠0）、读值越界（不在合理温度区间）或读数长期不动时，才触发一次探测：枚举 `T*` 温度候选 → 起 1–2 s 单线程 `DispatchQueue(qos: .userInteractive)` 负载 → 取涨幅最大的键（本机唯一选出 `Tp0j`，+19.3 °C）。探测结果缓存到磁盘（含机型与系统版本），换机器或系统升级后自动重探。探测会短暂占用一个核心，触发时在界面上给出提示（"正在识别温度传感器…"），且必须可取消。

**4. 降级链（完整形态）**：

```
libSMC 读 Tp0j（及降级键）  →  失败则 thermalState 四档  →  再失败则「不可用（原因）」
```

每一级都写明触发条件与界面文案；**任何一级都不得编造数字**：读不到就是"不可用 + 原因"，不得显示 0，也不得用热压力等级反推温度。

**5. 可信度标注**：键语义属"负载相关性推断"而非 Apple 确认，且**无法交叉验证**（powermetrics 只给压力等级；Apple 未公开 die 温度↔SMC 键对照表）→ 界面上的核心温度**必须标"近似值"并显示传感器名**（如「核心温度 56.8 °C · SMC Tp0j · 近似值」）。这不是权宜之计，是长期事实。

**6. 热压力等级独立成行**：四档（正常/轻度/重度/关键），**不叫"温度"**，与核心温度并列显示，读者一眼能分清"这是等级不是度数"。

**7. SoC 封装热点**：悬浮窗里**并列显示两个温度**——「核心温度（SMC Tp0j · 近似值）」与「SoC 热点（SMC TVD0 · 近似值）」。后者是这台机器真正的热天花板（单核满载 73 °C，比核心温度的 65 °C 更接近降频边界），对"电脑健康"更有意义。**菜单栏迷你读数只显示核心温度**（保持一行紧凑）。

**8. 不引入特权组件**（票 21）：温度、功耗都不靠 root。功耗 mW 因此出局。
