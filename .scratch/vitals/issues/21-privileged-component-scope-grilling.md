# 要不要为"功耗"装一个特权组件

## Question

票 01 找到 `/usr/lib/libSMC.dylib` 后，**温度已经不需要特权了**——无特权就能读数值温度（Tp05/Tp09 实测随 CPU 负载上升）。所以特权组件剩下的唯一用途是**功耗（mW）**。问题因此变得很简单：

**为了一个"CPU 此刻耗多少瓦"的数字，值得在你自己的机器上常驻一个 root 守护进程吗？**

候选：

- (a) **不装任何特权组件**：v1 全部指标都走无特权后端；功耗这一格显示"不可用（需特权）"，或者干脆不占界面位置；功耗的用法写在文档里（"想看就自己跑一次 `sudo powermetrics --samplers cpu_power`"）。
- (b) **装可选的特权组件**：沿用已定的安全边界（LaunchDaemon + unix socket + 固定动作枚举 + 对端 uid 校验 + 审计日志），只提供功耗查询；不装也能用，菜单里给安装入口。
- (c) **一次性手动采样**：不做常驻组件，菜单里提供"以管理员身份运行一次并把结果贴回来"的一次性采样流程。

要一并定下：

- 功耗这一格在悬浮窗里的位置：并入"电源状态"卡片，还是干脆不在 v1 出现。
- 若做 (b)：组件的职责边界（只做功耗一个动作）、安装方式（.pkg 里可选勾选）、卸载是否干净。
- 若不做：GLOSSARY 里"特权组件"这个词是否还成立、ADR 第二篇写什么（"为何不装特权组件"而不是"特权组件的机制"）。

产出：结论 + 对票 14（特权组件）、票 15（.pkg 内容）、票 16（ADR 篇目）的直接影响。

## Answer

**决定：不装任何特权组件。** 票 01 证明温度可以无特权读到（`/usr/lib/libSMC.dylib`），于是"为了一个瓦数在你机器上常驻一个 root 守护进程"这件事不值得——本项目**不引入任何特权组件**。

连带影响（已同步到地图）：

- 票 14（特权组件）作废关闭，见其答案；地图的"Out of scope"记录了这条边界。
- 票 15：`.pkg` 只装 `Vitals.app` + 用户级 LaunchAgent，**不含任何 LaunchDaemon**，安装时也不再需要管理员密码。
- 票 16：ADR 第二篇改为《为何不引入特权组件》——记录取舍本身：公开 API 拿不到数值温度、私有 dylib 免特权即可、私有组件只剩功耗一个用途，不值得。
- 票 09：温度后端改为无特权实现，能力探测 + 自动降级。
- GLOSSARY：「特权组件」这个词从术语表里移除——项目里不再存在这个东西。

**同轮附带确定的三件事**（属于票 04 的后端选型，已写进票 04）：

1. **接受在应用里 dlopen 私有 dylib** `/usr/lib/libSMC.dylib`（`SMCOpenConnectionWithDefaultService` / `SMCReadKeyAsNumeric` / `SMCGetKeyInfo`），前提是启动时做能力探测（dlopen 失败、符号缺失、连接失败、键不存在、读值越界），任何一步失败都自动降级为热压力四档并在界面写明原因。
2. **温度可信度标注**：若票 23 最终只能靠负载相关性**推断**出 CPU die 键，界面照常显示读数，但必须标为**近似值**并显示实际传感器名（如「Tp05·近似」），不得冒充权威值。
3. **热量与温度的区分**：热压力等级独立成行、四档、**不叫"温度"**；温度类阈值告警在后端不可用时按"不可用"处理，不得静默不触发；等级类告警保留。
