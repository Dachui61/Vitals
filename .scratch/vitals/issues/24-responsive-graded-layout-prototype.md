# 悬浮窗的响应式分级布局

## Question

票 05 定稿的是"固定八段布局"，但用户随后要求悬浮窗**可以随意拖动位置、缩放到任意大小，并且随大小精简内容**。这需要一套明确的分级规则：每个尺寸档显示哪些区块、档位之间怎么切换。

**分级顺序（用户指定，由小到大）**：

| 档 | 内容 |
|---|---|
| L0 | **一行文字**：CPU 占用 · 温度 · 内存 |
| L1 | 小卡片：CPU、核心温度、内存、GPU 占用 |
| L2 | 小卡片：电源、磁盘、网络 |
| L3 | 核心温度卡（大数字 + SoC 热点 + 热压力等级） |
| L4 | 进程 Top 5 卡片 |
| L5 | 每核占用（12 条曲线） |

要确定并原型验证：

1. **分档依据**：按宽度、还是按面积、还是宽高同时看？每个档的最小尺寸（低于它就退到上一档）是多少？
2. **退档规则**：高度不够时如何优雅降级（直接藏起来，还是换成更紧凑的排版）？
3. **L0 单行的确切内容与格式**：一行文字怎么排（分隔符、字重、温度是否变色）？在最小尺寸（约 240×40）下放得下几个数字？
4. **档位切换的视觉**：切换时内容淡入淡出还是瞬时？要不要显示当前档位（正式版多半不显示）。
5. **拖拽与缩放手感**：无边框窗口下哪里能拖、哪里能改大小；最小尺寸是多少；是否需要显式的缩放握把。

产出：可运行的原型（更新 `prototypes/VitalsPanelPrototype.swift`），能拖、能缩，能演示 L0→L5 的全部档位；截图存 `prototypes/`。

## Answer

**响应式分级已实现并在原型中验证**（截图：[prototypes/vitals-responsive-levels.png](../../../prototypes/vitals-responsive-levels.png)，逐档：[level-L0..L5](../../../prototypes/)；源码 `prototypes/VitalsPanelPrototype.swift`）。

**分级规则**：宽、高各算一个"允许的最高档"，**取小者**为实际档位——所以又宽又矮的窗口会退档，而不是把内容压扁。

| 档 | 宽度上限 | 高度下限（= 该档内容的实测最小高度） | 内容 |
|---|---|---|---|
| L0 | < 320 | ≥ 46 | **一行文字**：CPU 占用 · 温度 · 内存 |
| L1 | < 520 | ≥ 120 | 小卡片：CPU / 核心温度 / 内存 / GPU 占用 |
| L2 | < 700 | ≥ 200 | 小卡片：电源 / 磁盘 / 网络 |
| L3 | < 880 | ≥ 400 | 核心温度卡（大数字 + SoC 热点 + 热压力等级 + 阈值带） |
| L4 | < 1080 | ≥ 660 | 进程 Top 5 卡片 |
| L5 | ≥ 1080 | ≥ 660 | 每核占用（12 条曲线） |

（高度阈值即"装得下"的下限；**高度不够就退档**，而不是让内容被裁掉。）

**其它定稿**：

- **L0 一行的确切格式**：`CPU 13% · 温度 57° · 内存 63%` —— 标签用次级色、数值用主色，**温度按阈值变色**（≥70 黄、≥80 红），分隔符是居中的「·」。L0 不显示标题栏（没有空间），关闭靠菜单栏图标或 ⌘Q。
- **窗口**：`borderless + .resizable`，`minSize = 230×34`（L0 的最小尺寸），`maxSize = 4000×3000`，`isMovableByWindowBackground = true`（拖背景即拖动，可拖到任意显示器），默认 560×200。
- **缩放手感**：无边框窗口在边缘/角落自带缩放光标即可拖拽改大小；**正式版要在右下角加一个显式的缩放握把**（原型未加，是给实现票的明确要求）。
- **滚动兜底**：正常情况下各档都刚好放下，不出现滚动条；万一溢出（字体缩放、极窄窗口）可滚动且隐藏滚动条。
- **档位切换**：整块出现/消失，**瞬时**；正式版用 0.15s 交叉淡化（避免闪烁）。

**给票 12 的增量要求**：票 05 的"固定八段布局"被本票取代 —— 实现时按上面的分档表组织视图，而不是写死一个长 VStack。
