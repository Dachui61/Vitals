# 2. 为何不引入特权组件

- 状态：已接受
- 日期：2026-11-14
- 相关票据：02 / 14 / 20 / 21

## 上下文

早期方案里，数值温度被认为需要特权：helper 以 root 跑，由 launchd 拉起，通过 unix socket 提供只读查询；安全边界定为"键名白名单 + 校验对端 uid + socket 0600 + 审计日志"。

后来票 01 找到了免特权路径（`/usr/lib/libSMC.dylib`），特权组件的**唯一剩余用途**是功耗（CPU/GPU/ANE 功率 mW，`powermetrics --samplers cpu_power` 需要 root）。

## 决策

**本项目不引入任何特权组件**：没有 root LaunchDaemon、没有 unix socket、没有审计日志、没有 `.pkg` 里的管理员密码。功耗 mW 随之出局（改称"不可用"或干脆不占界面位置）。

## 后果

- 安装变成**双击即装**，不需要管理员密码；卸载只清理 app 与用户级 LaunchAgent。
- 攻击面显著缩小：用户机器上没有常驻的 root 进程，也不需要 app 自己做提权。
- 代价：拿不到功耗（瓦）。对"电脑健康"这个目标而言，温度、占用、内存压力比瓦数更有信息量。
- 如果将来 libSMC 被 Apple 撤掉，退路是重新评估特权路线——那时 ADR 1 的降级链会先接管（显示热压力四档 + 说明原因），不会静默失败。

## 备选方案（被否掉的）

| 方案 | 否掉原因 |
|---|---|
| 装可选的功耗 helper | 为一个瓦数常驻一个 root 守护进程，收益与风险不成比例（票 21） |
| 一次性手动采样（`sudo powermetrics`） | 交互摩擦大，且省不下多少；不如文档里写一句让用户自己跑 |
| 让整个 app 以 root 运行 | 安全上不可取 |
| 装第三方传感器二进制 | 违反"不依赖第三方二进制"，且这些工具走已死的经典 SMC 路径 |
